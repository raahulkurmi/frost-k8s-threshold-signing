# Claims audit

Each row is a claim from the papers about this project (Paper 1, Paper 3) or the KEP-740
findings. The verdict applies to **what the claim says about the prototype the papers
describe** (the FROST prototype, now in `legacy/frost/`, code as of commit `7692d5a` on
`main`). Where the rebuilt system (threshold RSA, branch `fix/threshold-rsa`) changes the
answer, the last column says what is true now, with evidence.

Verdicts: **TRUE**, **FALSE**, **NEEDS-REWORD**, **SUPERSEDED**. Legacy line numbers refer
to `legacy/frost/…` (each file there gained a two-line `//go:build legacy` header; the
original code is at `git show 7692d5a:<path without legacy/frost/>`).

| # | Claim (source) | Verdict | Evidence | What is true now (rebuilt system) |
|---|---|---|---|---|
| 1 | "The coordinator holds no signing key material" (Paper 3 §3.1, §8.3, §10) | **FALSE** | The old coordinator loaded a P-256 **private** key and signed every JWT with it: `legacy/frost/cmd/grpc-proxy/main.go:228` (`signing.NewECDSAKey`), `:205` (`ecKey.SignES256`). It also decoded all 5 secret shares: `git show 7692d5a:internal/coordinatorstate/bootstrap.go` lines 40–56 (D5) | **TRUE now.** The coordinator loads only `public-meta.json`, the policy and its mTLS keys (I3). Evidence: T12 `TestCoordinatorHasNoSecretTypes` (go list + AST), T13 `scripts/check-images.sh` plus negative control, L4 (coordinator host holds no share), C4 (Phase 9) |
| 2 | "Converts the Schnorr signature to IEEE P1363" (Paper 3 §3.2) | **FALSE** | No conversion of a Schnorr signature exists, and none is possible (`legacy/frost/README.md` "Why FROST was abandoned" §3). The P1363 encoding in the code is applied to a **separate ECDSA** signature: `legacy/frost/internal/signing/ecdsa.go:61–71` (`SignES256`, "IEEE P1363 format: R ‖ S"). There is no signature conversion; the combined Shoup signature **is** the RSASSA-PKCS1-v1_5 signature (spike, T1) |
| 3 | "Group public key exported in PKIX to `ecdsa-signing.pem` for FetchKeys" (Paper 3 §5.4) | **FALSE** | `ecdsa-signing.pem` held an **EC PRIVATE KEY** (verified without printing it: file header `-----BEGIN EC PRIVATE KEY-----`, NOTES/Phase 1; history commits 93f0dc5, 496ce83). Evidence: T1 `TestIssuedJWTVerifiesWithFetchKeysOnly`, `TestFetchKeysPKIXRoundTrip` (R-a), E5 (`/openid/v1/jwks` modulus equals public-meta) |
| 4 | "Min. compromises to forge: 3" and "Coordinator compromise → requires t compromises" (Paper 3 Tables 1, 4) | **FALSE** (for the prototype) | One file (`ecdsa-signing.pem`) or one coordinator compromise sufficed to forge any token, offline and forever (claims 1 and 3). Correct wording: "offline forgery requires compromising ≥ 3 signers; while an attacker controls the coordinator it can obtain tokens for claims the signers' policy allows" (docs/THREAT_MODEL.md §4, §7) |
| 5 | "Test A: coordinator compromise cannot enable forgery" (Paper 3 §4.4) | **FALSE** | Given claims 1 and 3, a coordinator compromise *was* a forgery. Nothing in the prototype's tests exercised a compromised coordinator. The old signers signed whatever the coordinator sent (D11): `git show 7692d5a:cmd/signer/main.go` `signHandler` has no claims validation | **NEEDS-REWORD.** Evidence now: T7 `TestSignerPolicyRejectsCoordinatorBypass` (a caller with the real coordinator cert gets 0/5 shares for policy-violating claims), T6, N14; C2 and C4 in Phase 9. Say "cannot enable forgery of policy-violating tokens, nor any forgery after control is lost" |
| 6 | "Schnorr-signed JWT serialized as ES256" (Paper 1 §VII-B, §VIII-C) | **FALSE** | The JWTs were ECDSA-signed by one key and labelled ES256: `legacy/frost/cmd/grpc-proxy/main.go:180` (`"alg":"ES256"`), `:205`. A Schnorr signature cannot verify as ES256 under any key (`legacy/frost/README.md` §3) | Tokens are RS256, and their signature is the threshold-combined RSA signature (I1: T1, T2, E1) |
| 7 | "Threshold ECDSA less practical than FROST" (Paper 1 §VII-B) | **NEEDS-REWORD** | The comparison is framed wrongly for this use: FROST **cannot** produce any signature Kubernetes accepts (RS256/ES256/ES384/ES512 only: `pkg/serviceaccount/externaljwt/plugin/plugin.go:180` at v1.36.5), so it is not a practical option at all. Threshold ECDSA *could* produce ES256, but the maintained Go implementation (`taurusgroup/multi-party-sig`, CGGMP21) supports only secp256k1, which Kubernetes does not accept (no ES256K) | The implemented option is threshold **RSA** (Shoup), which yields RS256 natively and needs no interactive nonce rounds. Suggested wording: "for Kubernetes, FROST is excluded by the algorithm allow-list; threshold ECDSA on P-256 lacks a maintained Go implementation; threshold RSA works without changes to Kubernetes" |
| 8 | "40× improvement" (Paper 3 §1, §4.2, §10) | **NEEDS-REWORD** | The ratio is not a constant. For independent node compromise probability p, P(single key compromised) = p and P(≥ t of n compromised) ≈ C(n,t)·p^t for small p, so the ratio is **1 / (C(n,t)·p^(t−1)) = 1/(10p²)** for t=3, n=5. It **equals 40 only at p = 0.05**; at p = 0.01 it is 1000, at p = 0.1 it is 10. It also assumes independent compromise, which the tested deployments do not provide (docs/THREAT_MODEL.md §6) | Report the formula and the independence assumption, not "40×" |

| 10 | Finding 2: DER vs IEEE P1363 for ECDSA signatures (issue #141669) | **TRUE as an integration lesson; irrelevant to the signing path now** | RFC 7518 §3.4 requires `R ‖ S`.
